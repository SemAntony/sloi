# Sloi UI: Vision & Principles

Статус: **черновик** (A1, 2026-11-13). Правит владелец; после правки статус меняется на «принято».
Связанные документы: [ROADMAP](../../devepop-docs/ROADMAP.md), [Governance](../governance/index.md), [Tokens README](../../packages/tokens/README.md).

## 1. Зачем это нужно

Sloi UI — библиотека интерфейсных компонентов и дизайн-токенов для продуктов Sloi: формы, таблицы, админские паттерны.
Цель — чтобы продуктовая команда собирала экран из готовых частей, не решая заново вопросы доступности, тем, состояний и API.

Для кого:

1. **Разработчик продукта** на React/Next.js: ставит пакет, получает компоненты, которые работают без собственных reset-стилей и обёрток.
2. **Автор библиотеки** (сейчас один человек): ему нужен план, в котором каждая задача мала, проверяема и не ломает уже сделанное.

## 2. Позиционирование

Сейчас Sloi UI — **React design system с кросс-платформенным архитектурным направлением**.

- «Cross-platform» не заявляется, пока нет первой проверенной второй реализации (A8). До тех пор это направление, а не свойство продукта.
- Конкуренты по полке: shadcn/ui, Mantine, Chakra, Radix Themes. Выигрывать нужно не количеством компонентов, а цельностью: единые токены, доступность по умолчанию, сильные таблицы и формы, удобное подключение.

### Ориентиры

Берём у зрелых систем конкретные решения, а не объём компонентов.

| Система | Что перенимаем | Где применяем |
| --- | --- | --- |
| Microsoft Fluent 2 | Архитектура: global и alias токены, темы и high contrast, разделение платформенных реализаций | A2, A5, A8 |
| IBM Carbon | Инженерная зрелость: доступность, документированные правила, governance | A3, `docs/governance/*` |
| Material 3 | Визуальная система: семантические токены, согласованность состояний | A4, A5 |
| Shopify Polaris | Практика: админские интерфейсы, формы и таблицы, документация | D40, DataTableV2 |

## 3. Принципы

Каждый принцип дан в формате «что значит» и «что не значит», чтобы им можно было пользоваться при споре.

### 3.1. React-first, cross-platform-ready

- Значит: сначала качественный React-продукт. Решения (токены, контракты API, поведение) принимаются так, чтобы их можно было переиспользовать на другой платформе.
- Не значит: строить заготовки под ненаписанные платформы. Если решение усложняет React сейчас ради гипотетической платформы, оно откладывается.

### 3.2. Tokens-first

- Значит: единый источник токенов в формате DTCG; CSS, TypeScript и JSON генерируются из него. Компонент не использует сырые значения (цвет, отступ, радиус), только токены.
- Не значит: токены на каждый компонент сразу. Третий слой (component tokens) сначала пробуется на одном компоненте (A4).

### 3.3. Accessibility by design

- Значит: доступность входит в критерий готовности компонента, а не «улучшается потом». Контраст токенов проверяется автоматически (A3), поведение клавиатуры и ARIA проверяется тестами (axe) и в Storybook.
- Не значит: «axe зелёный = доступно». Автоматика ловит часть проблем; остальное для Tier-1 компонентов проверяется руками.

### 3.4. Reuse proven behavior

- Значит: сложное поведение (фокус-менеджмент, позиционирование, типовые ARIA-паттерны) берётся из зрелых решений: Radix сейчас, React Aria и Zag.js как кандидаты (A7).
- Не значит: «одна библиотека на всё навсегда». Выбор делается по конкретным компонентам и фиксируется коротким RFC.

### 3.5. Incremental architecture

- Значит: архитектура растёт вместе с реальными потребностями; каждое решение привязано к задаче, которая его требует.
- Не значит: перестройка monorepo, универсальный state-пакет или генерация Swift/Kotlin «на будущее».

### 3.6. Product before monetization

- Значит: сначала сильные компоненты, таблицы, формы, админские паттерны и удобство интеграции (README, примеры, понятные ошибки типов).
- Не значит: лицензия и тарифы откладываются навсегда; к ним возвращаемся, когда есть что продавать.

## 4. Платформенная стратегия

Архитектура строится слоями; каждый слой можно использовать отдельно от верхних.

| Слой | Пакет / место | Состояние сегодня |
| --- | --- | --- |
| Токены | `@sloi/tokens` | Источник истины: CSS (`palette.css`, `colors.css`, `tokens.css`, `typography.css`); `tokens.json` и `tokens.js` генерируются regex-скриптом. Тёмная тема есть (`[data-theme='dark']`). Цель: DTCG как источник (A2). |
| Поведение | `@sloi/headless-core` | Контроллеры состояния: Dialog, Select, Tabs, Tooltip, Combobox, `useControllableState`. |
| React-компоненты | `@sloi/ui-kit` (`src/shared/ui`) | Основной продукт: обёртки над Radix, SCSS modules, Storybook, unit + a11y тесты. |
| Другие платформы | `@sloi/lit-wrappers` | Заглушка: экспортирует только статус и scope, компонентов нет. Заморожено (D36). |

Этапы:

1. **Сейчас:** React. Токены и поведение отделены от компонентов ровно настолько, насколько это уже сделано.
2. **Затем:** токены в DTCG (A2), проверка контраста (A3), модель тем (A5), контракт Button (A6).
3. **Только при реальной потребности:** оценка поведенческого ядра (A7) и proof-of-concept на React Native с одним Button (A8). Только после A8 решается вопрос о нативных форматах токенов.

## 5. Чего мы не делаем сейчас

- Не перестраиваем monorepo под будущие платформы.
- Не пишем универсальный state-пакет и не переписываем React-компоненты ради переносимости.
- Не вводим component tokens для всех компонентов сразу.
- Не делаем Figma-плагин и не пишем RFC на решения, по которым нет спора.
- Не генерируем Swift/Kotlin.
- Не добавляем новые компоненты до конца Фазы 2 (см. ROADMAP).

## 6. Как принимаются решения

Предложение проходит четыре вопроса; если на любой ответ «нет», решение откладывается или упрощается:

1. Решает ли оно реальную боль (из `docs/adoption/pain-points.md`, из тестов, из потребителя), а не гипотетическую?
2. Укладывается ли в принципы выше, особенно в «tokens-first» и «accessibility by design»?
3. Можно ли проверить результат автоматически (тест, скрипт, сборка)?
4. Можно ли сделать это за одну сессию или разбить так, чтобы можно было?

## 7. Как понять, что это работает

- Чистый Next.js-проект ставит пакет и собирает страницу с формой и таблицей без собственных reset-стилей и без ошибок типов (проверяется в `sloi-smoke`).
- Все пары токенов проходят WCAG 2.2 AA в каждой теме (A3).
- Каждый Tier-1 компонент имеет unit + a11y тесты и документированный API.
- CSS-контракт `@sloi/tokens` (имена `--sloi-*`) не ломается при смене источника токенов.
- Компоненты не используют физические `left`/`right`, `margin-left` и т.п. там, где нужны логические свойства; страница в `dir="rtl"` не ломается (D42).

## 8. Открытые вопросы для владельца

1. Верна ли формулировка позиционирования в разделе 2? Нужно ли называть конкурентов явно?
2. Подходит ли список «не делаем сейчас» (раздел 5) или что-то нужно вернуть в план?
3. Публичный адрес документа: оставляем в `docs/architecture/` или переносим в корень README при релизе (D37)?
4. Кто целевой потребитель в ближайший год: внутренние продукты Sloi или внешние команды? От этого зависят приоритеты D29–D37.
5. Нужна ли полноценная поддержка RTL (арабский, иврит) или достаточно не закрывать её архитектурно? Дешёвая проверка логических свойств описана в D42.
