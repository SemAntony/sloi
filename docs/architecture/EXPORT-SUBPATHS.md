# D29. Решение по подпутям экспорта

Статус: принято 2026-11-22. Реализация: D30. Бюджеты и gate: `docs/governance/multi-framework-readiness.md`.

## 1. Контекст и цифры

Сейчас у пакета один вход `.` (`export * from './shared/ui'`) и два CSS: `./styles.css`, `./base.css`.
Замер `dist/` (сборка от 2026-11-18):

| Что | Raw | Gzip |
|---|---|---|
| `dist/index.js` целиком | 276 KB | 59 KB |
| `react-day-picker` + `date-fns` + `@date-fns/tz` (всё ради DatePicker) | ≈120 KB | ≈28 KB |
| `dist/style.css` | 116 KB | 17.5 KB |
| из него CSS `react-day-picker` | 8.9 KB | 1.8 KB |

Одна зависимость одного компонента даёт около 43% JS-бандла. Это и есть проблема, которую решаем.
Вес собственного кода DataTableV2 этим замером не получен (разметка модулей в бандле неполная), его измерили отдельно в D30 (шаг 1), см. ниже.

Те же настройки, что у боевой сборки; `react-day-picker`, `date-fns`, `@date-fns/tz` внешние. База: один вход, всё вшито (на сегодняшнем коде).

| Чанк | Raw | Gzip |
|---|---|---|
| База: `index.js` (всё вшито) | 236 KB | 54.8 KB |
| `index.js` (корень без DataTableV2 и DatePicker) | 81 KB | 19.7 KB |
| `data-table-v2` (собственный код) | 48 KB | 13.9 KB |
| `date-picker` (собственный код) | 3.6 KB | 1.5 KB |

| Сумма всех чанков | 137 KB | 36.5 KB |
| `style.css` | 110.6 KB | 16.7 KB |

Выводы:
- Вынос `react-day-picker` + `date-fns` + `@date-fns/tz` даёт −99 KB raw (−42%) и −18.3 KB gzip (−33%) для того, кто DatePicker не использует. Прежняя оценка «59 → 31 KB gzip» была занижена: реально ≈36.5 KB.
- **DataTableV2 проходит критерий 2.1.2** (13.9 KB gzip > 10): получает подпуть `./data-table-v2`. DatePicker проходит критерий 2.1.1 (сторонний рантайм), хотя его собственный код всего 1.5 KB gzip.
- Общий код (`popover` и др.) Rolldown выносит в общие чанки автоматически, дублей между входами нет.
- Риск CSS подтверждён: в чанке `date-picker` остаётся `import "react-day-picker/style.css"`, а из `style.css` пропали 8 KB CSS `react-day-picker`.

## 2. Решения

### 2.1. Модель: core + heavy
- **Core** (корневой вход `@sloi/ui-kit`): компоненты, у которых нет тяжёлых сторонних зависимостей. Остаётся главным входом.
- **Heavy** (свой подпуть, например `@sloi/ui-kit/date-picker`): компонент выносится, если выполняется **любое** из условий:
  1. тянет сторонний рантайм, которого нет в core (`react-day-picker`, графики, редакторы, виртуализация и т.п.);
  2. его собственный код весит больше 10 KB gzip.

Подпути именуются по имени компонента в kebab-case (`/date-picker`, `/data-table-v2`). Лёгкие компоненты (`/button` и т.п.) подпутей **не получают**: tree-shaking в корне справляется, а лишние входы это лишняя поверхность API и поддержки.

### 2.2. Как объявлять тяжёлую зависимость
- Зависимость **не торчит** в публичном API (в `.d.ts` нет её типов, наружу не передаются её объекты) → `dependencies` + `external` в сборке (не вшивать в бандл). Потребителю ничего ставить вручную не нужно, его бандлер дедуплицирует копию.
- Зависимость **торчит** в API → `peerDependencies` + `peerDependenciesMeta: { "<name>": { "optional": true } }`.
- Для DatePicker действует первый случай: типы значений локальные (`DatePickerDateRange` объявлен у нас), `locale` это `string`. Это инвариант: его стережёт тест (см. 2.5).

Почему не вшивать и не делать peer: вшитая копия не дедуплицируется и раздувает бандл; peer заставляет каждого потребителя читать README и подбирать версии, хотя наружу библиотека не видна.

### 2.3. Совместимость: два шага
- **Шаг A (minor, без поломок):** добавить подпути, `react-day-picker`/`date-fns` вынести во внешние `dependencies`. Корень продолжает реэкспортировать DatePicker, но с `@deprecated` в JSDoc («импортируйте из `@sloi/ui-kit/date-picker`»). У JS пакета `sideEffects` ограничен CSS, так что неиспользованный DatePicker выбрасывается бандлером потребителя.
- **Шаг B (следующий major, через Changesets из D31):** убрать heavy-компоненты из корня. С этого момента корень физически не ссылается на тяжёлые зависимости, и gate (2.5) проверяет это тестом.

Корень нельзя «оставить с реэкспортом навсегда» при optional peer: бандлер падает на неразрешённом импорте ещё до tree-shaking. Поэтому два шага, а не один.

### 2.4. CSS
- Пока один `styles.css` (17.5 KB gzip). Сборка Vite в lib-режиме даёт один CSS, и для такого размера делить его не нужно.
- Правило на будущее: отдельный `./<component>/styles.css` появляется, только если CSS heavy-компонента больше 3 KB gzip. CSS `react-day-picker` ≈1.8 KB gzip → не делим. CSS DataTableV2 замерить в D30.
- **Риск для D30:** сейчас `date-picker.tsx` делает `import 'react-day-picker/style.css'`. После вынесения библиотеки во внешние зависимости этот импорт останется в JS пакета и будет требовать от бандлера потребителя обработки стороннего CSS. Его нужно оставить внутри нашего `styles.css` (через SCSS), а не внешним импортом.

### 2.5. Контроль
Бюджеты по каждому входу в `mf:validate` (корень, каждый подпуть) вместо одного общего числа. Тесты:
1. публичные `.d.ts` не импортируют сторонние типы тяжёлых зависимостей;
2. после шага B корневой бандл не содержит их кода;
3. `exports` не содержит подпутей, которых нет в `dist/`.

## 3. Как добавлять следующий тяжёлый компонент
1. Проверить критерии 2.1. Не проходит → остаётся в корне.
2. Объявить зависимость по правилу 2.2 и добавить во внешние в `vite.config.ts`.
3. Добавить вход в `lib.entry`, запись в `exports` (`import`/`require`/`types`) и бюджет в gate.
4. Реэкспорт в корне только с `@deprecated` до ближайшего major.
5. Строка в `CHANGELOG.md` / changeset, раздел в README.

## 5. Открытое
- Решено в D30: `typesVersions` не добавлен. Все наши потребители на `moduleResolution: bundler`, а `attw` для подпутей показывает только `node10: Resolution failed`. Если понадобится поддержка node10, добавить `typesVersions` с двумя подпутями (4 строки в `package.json`).
- Размер CSS `DataTableV2` отдельно не замерен: по правилу 2.4 делить `styles.css` нужно, только если он больше 3 KB gzip. Пока `styles.css` остаётся единым (17.7 KB gzip).
